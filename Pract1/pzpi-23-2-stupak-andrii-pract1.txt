3 ОПИС ВИКОНАНОЇ РОБОТИ
     3.1 Загальні відомості про шаблони (патерни) проєктування
     Шаблони проєктування - це типові рішення поширених проблем, які виникають під час проєктування архітектури програмного забезпечення. За класифікацією GoF вони поділяються на породжувальні, структурні та поведінкові. Вони не є готовим кодом, а являють собою концепцію, яку можна адаптувати під специфіку конкретної задачі, що підвищує гнучкість, масштабованість та підтримуваність системи.
     
     3.2 Опис обраного патерна
     Назва патерна: Strategy (Стратегія).
     Тип шаблона (патерна): Поведінковий шаблон.
     Основне призначення: Шаблон визначає сімейство споріднених алгоритмів, інкапсулює кожен із них у самостійний клас та забезпечує їх повну взаємозамінність. Це дозволяє змінювати алгоритм незалежно від клієнтських об'єктів, які його використовують.
     Передумови застосування: Використання патерна є доцільним у випадках, коли в системі існує кілька схожих класів, що відрізняються виключно своєю поведінкою. Також шаблон застосовується для усунення громіздких умовних операторів (if або switch), які відповідають за вибір необхідного алгоритму в межах одного масивного класу, та коли потрібно динамічно змінювати поведінку об'єкта під час виконання програми (в режимі Runtime).
     Переваги:
• відповідність принципу відкритості/закритості (Open/Closed Principle): нові стратегії можна додавати без модифікації існуючого коду контексту;
• ізоляція коду та даних алгоритмів від інших класів системи;
• заміна успадкування механізмом делегування;
• можливість зміни поведінки об'єкта під час виконання програми.
     Недоліки:
• ускладнення загальної архітектури системи внаслідок збільшення кількості класів;
• клієнтський код повинен володіти інформацією про відмінності між конкретними стратегіями для здійснення їх коректного вибору
     
     3.3 Структура шаблона (патерна)
     Опис структурних частин:
• Context (Контекст): клас, що зберігає посилання на об'єкт конкретної стратегії та працює з ним виключно через загальний абстрактний інтерфейс. Контекст не містить власної логіки виконання алгоритму.
• Strategy (Інтерфейс стратегії): визначає єдиний контракт (набір методів) для всіх варіацій алгоритму. Контекст використовує цей інтерфейс для виклику алгоритму, реалізованого в конкретній стратегії.
• Concrete Strategies (Конкретні стратегії): класи, що імплементують інтерфейс стратегії та містять безпосередню унікальну реалізацію певного алгоритму.
     Опис взаємодії об’єктів: 
     Клієнтський код створює об'єкт конкретної стратегії та передає його об'єкту Контексту (через конструктор або метод-сетер). Під час виконання своєї бізнес-логіки Контекст не виконує операцію самостійно, а викликає відповідний метод переданого йому об'єкта Стратегії (делегує виконання). При необхідності клієнт може замінити об'єкт стратегії в Контексті на інший, тим самим змінивши його поведінку.

Рисунок 3.1 – Паттерн «Стратегія» діаграма послідовності

     Ця діаграма послідовності показує, як патерн Стратегія змінює алгоритми на льоту під час роботи програми.
     Спочатку Клієнт передає в Контекст першу стратегію через метод setStrategy(StrategyA). Коли Клієнт викликає головну функцію doSomething(), Контекст просто перенаправляє цей виклик об'єкту ConcreteStrategyA, який самостійно виконує свою операцію та повертає результат назад.
     Потім Клієнт динамічно підміняє алгоритм, викликаючи setStrategy(StrategyB). При наступному запиті doSomething() той самий Контекст автоматично делегує роботу вже новій стратегії ConcreteStrategyB, яка виконує зовсім іншу логіку.
     Головна суть діаграми, що Контекст залишається незмінним, але його поведінка повністю керується Клієнтом через заміну об'єктів стратегій.

     3.4 Реалізація шаблона патерна
     Для реалізації шаблона обрано мову Java, яка завдяки вбудованій підтримці інтерфейсів дозволяє чітко розділити абстрактні стратегії поведінки та їхні конкретні реалізації. У прикладі розглядається система оплати в інтернет-магазині: об'єкт кошика (ShoppingCart) виступає контекстом, а різні варіанти оплати (через PayPal або банківську картку) - взаємозамінними стратегіями.
     На початковому етапі розробки необхідно визначити інтерфейс стратегії, який забезпечить взаємодію компонентів без їхньої жорсткої прив’язки до конкретних способів оплати. Це реалізується через створення інтерфейсу PaymentStrategy.
           public interface PaymentStrategy {
               void pay(double amount);
           }
     
     Інтерфейс PaymentStrategy виконує роль спільного знаменника для всіх майбутніх алгоритмів оплати. Він містить єдиний метод pay(), який кожна конкретна стратегія повинна реалізувати по-своєму. Такий підхід дозволяє дотриматися принципу інверсії залежностей (Dependency Inversion Principle): високорівнева логіка кошика залежить від абстракції, а не від конкретних реалізацій.
     На другому етапі всередині структури проєкту реалізується конкретна бізнес-логіка - класи, які безпосередньо виконують оплату, та контекст, який ними керує.
      18     public static class PayPalStrategy implements PaymentStrategy {
               @Override
               public void pay(double amount) {
                   System.out.println("Pay " + amount + " via PayPal");
               }
           }
       
           public static class CardStrategy implements PaymentStrategy {
               @Override
               public void pay(double amount) {
                   System.out.println("Pay " + amount + " via Card");
               }
           }
       
           public static class ShoppingCart {
               private PaymentStrategy paymentStrategy;
       
               public void setPaymentStrategy(PaymentStrategy strategy) {
                   this.paymentStrategy = strategy;
               }
       
               public void checkout(double amount) {
                   paymentStrategy.pay(amount);
               }
           }
     
     Класи PayPalStrategy та CardStrategy є вкладеними статичними класами, що реалізують інтерфейс стратегії. Їхній метод pay() описує дію, яку виконує система при виборі відповідного платіжного інструменту.
     Клас ShoppingCart виступає в ролі контексту. Він містить приватний атрибут paymentStrategy, типізований через інтерфейс. Динамічна зміна поведінки кошика досягається за допомогою сеттера setPaymentStrategy(). Метод checkout() просто делегує виконання завдання поточній встановленій стратегії, що дозволяє уникнути громіздких конструкцій if-else.
     Завершальним етапом є перевірка працездатності системи:
       public static void main(String[] args) {
           ShoppingCart cart = new ShoppingCart();
           PaymentStrategy paypal = new PayPalStrategy();
           PaymentStrategy card = new CardStrategy();
       
           cart.setPaymentStrategy(paypal);
           cart.checkout(1);
       
           cart.setPaymentStrategy(card);
           cart.checkout(5);
       }
     
     Сценарій демонструє головну особливість патерна Стратегія можливість гнучкої підміни алгоритмів під час виконання програми (Runtime). Спочатку об'єкт кошика cart конфігурується на роботу з paypal і виконує платіж через метод checkout(1). Потім, без зміни самого об'єкта кошика, йому "на льоту" підміняється внутрішня логіка на card, і наступний виклик checkout(5) виконується вже за іншим алгоритмом.

Покажи, як Клієнт взаємодіє з Контекстом, як спочатку викликається ConcreteStrategyA, а потім у Runtime підміняється на ConcreteStrategyB. Додай текстові нотатки, що Контекст просто делегує виконання.
     Результат (Згенерований PlantUML-код):
      1  @startuml
      2  skinparam style strictuml
      3  
      4  actor Client as "Клієнт"
      5  participant Context as "Контекст (ShoppingCart)"
      6  participant StrategyA as "ConcreteStrategyA (PayPal)"
      7  participant StrategyB as "ConcreteStrategyB (Card)"
      8  
      9  == Етап 1: Виклик першої стратегії ==
      10 Client -> Context: setPaymentStrategy(StrategyA)
      11 Client -> Context: checkout(amount)
      12 activate Context
      13 Context -> StrategyA: pay(amount)
      14 note right of StrategyA: Делегування алгоритму А
      15 activate StrategyA
      16 StrategyA --> Context: success
      17 deactivate StrategyA
      18 Context --> Client: return
      19 deactivate Context
      20 
      21 == Етап 2: Підміна в Runtime ==
      22 Client -> Context: setPaymentStrategy(StrategyB)
      23 note right of Context: Алгоритм змінено на льоту
      24 Client -> Context: checkout(amount)
      25 activate Context
      26 Context -> StrategyB: pay(amount)
      27 note right of StrategyB: Делегування нового алгоритму Б
      28 activate StrategyB
      29 StrategyB --> Context: success
      30 deactivate StrategyB
      31 Context --> Client: return
      32 deactivate Context
      33 @enduml
