3 ОПИС ВИКОНАНОЇ РОБОТИ
     3.1 Загальні відомості про систему
     Назва системи: Платформа для комунікації Discord.
     Розробник: Discord Inc. (засновники Джейсон Цитрон та Стен Вишневський).
     Призначення системи: Ігрова індустрія, корпоративна та повсякденна комунікація, дистанційне навчання, створення тематичних спільнот. Користувачі: Геймери, розробники, стрімери, студенти та будь-які онлайн-спільноти. Основні функції: Текстові чати з підтримкою каналів, високоякісний голосовий зв’язок із низькою затримкою, відеодзвінки, демонстрація екрана (стримінг), інтеграція з ботами та сторонніми сервісами, гнучка система керування ролями та доступами.
     
     3.2 Архітектурний стиль системи
     Архітектура Discord є гібридною і поєднує в собі декілька фундаментальних архітектурних стилів:
1. Мікросервісна архітектура (Microservices): Основна логіка системи розбита на сотні ізольованих сервісів, написаних на різних мовах програмування (Python, Go, Elixir, Rust), кожен з яких відповідає за свою задачу (сервіс статусів, сервіс розсилки сповіщень, сервіс каналів тощо).
2. Подієво-орієнтована архітектура (Event-Driven Architecture): Оскільки Discord працює в режимі реального часу, вся взаємодія побудована на шинах повідомлень та подіях. Події (наприклад, "користувач написав повідомлення" або "зайшов у голосовий канал") миттєво транслюються підписникам.
3. Клієнт-серверна архітектура (з товстим клієнтом): Клієнтські додатки (Electron для десктопа, React Native для мобільних) беруть на себе значну частину рендерингу та локальної обробки даних, взаємодіючи з серверами через гнучкі протоколи.
     Обґрунтування вибору архітектури: Звичайна монолітна або проста шарова архітектура не здатна впоратися з навантаженням Discord (мільйони одночасних користувачів та мільярди повідомлень на добу). Мікросервіси дозволяють масштабувати окремі вузли незалежно один від одного. Подієво-орієнтований підхід та використання WebSocket-з'єднань є єдиним способом забезпечити нульову затримку (Low Latency), яка є критичною для геймерів під час голосового зв'язку та чату.
     
3.3 Основні компоненти системи
  3.3.1 Інтерфейс користувача
     Інтерфейс користувача побудований за допомогою кросплатформних технологій. Десктопний додаток використовує фреймворк Electron (комбінація Chromium та Node.js) із бібліотекою React. Мобільні додатки реалізовані на React Native. Це дозволяє компанії перевикористовувати бізнес-логіку між різними платформами.
     3.3.2 Серверна частина
     Серверна частина: Точка входу для мільйонів клієнтів. Використовує сервери шлюзів (Gateway Servers) на базі Elixir, які тримають мільйони постійних відкритих WebSocket-з'єднань. Вони миттєво просувають події від backend-сервісів до конкретних користувачів.
3.3.3 Рівень бізнес-логіки
     Складається з багатьох спеціалізованих сервісів. Історично критична бізнес-логіка (керування серверами, користувачами) писалася на Python. Проте високонавантажені сервіси (наприклад, сервіс відстеження статусів "Read States" або сервіс маршрутизації голосових пакетів) переписані на Go та Rust задля максимальної швидкодії та ефективного керування пам'яттю.
3.3.4 Рівень зберігання даних
     Discord використовує розподілену систему баз даних. Основне схоже для повідомлень чатів базується на ScyllaDB (раніше Cassandra) - NoSQL СУБД, яка ідеально підходить для лінійного масштабування та запису терабайтів даних. Для збереження реляційних даних (профілі користувачів, налаштування серверів) використовуються кластери PostgreSQL. Для швидкого кешування та черг повідомлень застосовується Redis.
     3.3.5 Допоміжні сервіси
     Окрема велика підсистема - Discord Voice. Голосові сервери написані на C++ та Elixir і базуються на протоколі WebRTC / SFU (Selective Forwarding Unit). Вони не міксують аудіо на сервері, а просто з мінімальною затримкою перенаправляють зашифровані звукові пакети між учасниками голосового каналу.
     
     3.4 Взаємодія компонентів
     3.4.1 Загальний опис взаємодії за компонентною схемою
     Взаємодія підсистем Discord оптимізована для забезпечення мінімальної затримки (Low Latency), підтримки мільйонів одночасних з'єднань та розв'язання «проблеми великих серверів» (Big Server Problem), коли одна подія на сервері з мікрофонним чи текстовим спамом може створити лавиноподібне навантаження (Thundering Herd) на всю інфраструктуру.
	
Рисунок 3.1 – Діаграма компонентів системи «Discord»

     Відповідно до загальної архітектурної схеми проєкту, потоки даних розділені на три ізольовані рівні:
• Вхідний потік та захист (Edge): Усі клієнтські додатки (React Native / React / Electron) здійснюють початкові запити через крайову інфраструктуру Cloudflare. Це забезпечує захист від DDoS-атак, маршрутизацію DNS та кешування статичного контенту за протоколом HTTPS.
• Текстовий стек та події реального часу (Entry & Data): Для обміну повідомленнями та синхронізації статусів клієнти встановлюють постійні двосторонні з'єднання за протоколом WSS (WebSockets) із сервером шлюзу WebSocket Gateway. Пошукові запити індексуються та обробляються через ElasticSearch, тоді як трильйони сирих повідомлень чатів записуються в NoSQL сховище ScyllaDB.
• Оптимізація бізнес-логіки (Backend): Стандартне REST API платформи побудоване на базі Python Monolith. Проте високонавантажені операції та взаємодія з базами даних делеговані низькорівневому сервісу Data Service (Rust).
• Голосовий медіа-потік (Media): Коли користувач підключається до голосового каналу, шлюз передає команду на рівень Signaling. Відбувається швидкий обмін метаданими, після чого клієнт перемикається на пряму взаємодію з Media Router (C++ / Elixir). Передача аудіо, відео та демонстрації екрана відбувається повністю в обхід основних баз даних за допомогою протоколів WebRTC / Media UDP через архітектуру SFU (Selective Forwarding Unit) без перекодування на сервері.

     3.4.2 Ключові архітектурні механізми оптимізації взаємодії
     Для мінімізації затримок та захисту баз даних у межах описаної структури реалізовано три специфічні механізми:
• Асинхронний Fan-Out (Розмноження подій): Кожен користувач має свій довгоживучий процес сесії в Erlang VM (Elixir), а кожен сервер (Guild) свій окремий керуючий процес. Коли надходить повідомлення, процес гілди паралельно розсилає його по pids (ідентифікаторах процесів) усім активним сесіям, які, у свою чергу, проштовхують його клієнтам через WebSockets.
• Пасивні сесії (Passive Sessions) для економії трафіку: Близько 90% сесій на великих серверах є пасивними. Якщо користувач не відкрив вкладку конкретного сервера, шлюз не надсилає йому повний потік повідомлень. Сесія «апгрейдиться» до активної лише тоді, коли користувач переходить на канал, що знижує утилізацію смуги пропускання на 20%.
• Коалесценція запитів (Request Coalescing) через Rust Data Service: Коли тисячі користувачів одночасно запитують одне й те саме повідомлення (наприклад, після згадки @everyone), система не робить тисячі запитів до ScyllaDB. Спеціальний сервіс на Rust перехоплює ці запити, поєднує їх в один «in-flight» запит до бази даних, а потім розсилає єдиний отриманий результат усім підписникам через gRPC.

     3.5 Масштабованість та надійність
     Аналіз еволюції архітектури Discord дозволяє виділити кілька фундаментальних уроків масштабування надскладних розподілених систем:
• Еволюційний підхід до баз даних (Mongo, Cassandra, ScyllaDB): На етапі MVP Discord використовував MongoDB для швидкості розробки. Зі зростанням обсягів даних відбувся перехід на Cassandra, а при досягненні трильйонів повідомлень, на ScyllaDB. Це дозволило позбутися «stop-the-world» пауз збирача, які руйнували гнучкість системи реального часу, та перейти на по-процесорне шардування (per-core sharding).
• Відмова від Garbage Collection у критичних вузлах (Міграція на Rust): Сервіси з надвисокою інтенсивністю запитів (наприклад, сервіс статусів «Read States», який раніше працював на Go) були повністю переписані на Rust. Це стабілізувало графіки завантаження CPU, прибравши регулярні піки, спричинені очищенням пам'яті в Go/Python.
• Сортовані ідентифікатори (Twitter Snowflake): Використання 64-бітних ідентифікаторів на основі часових міток (з власною епохою компанії від 2015 року) дозволяє клієнтам та серверам сортувати повідомлення за часом створення та визначати дату відправки взагалі без звернення до бази даних.
• Апаратно-програмна оптимізація: Щоб обійти обмеження хмарних дисків Google Cloud Platform, інженери створили віртуальну абстракцію «Super-Disk», що об'єднує RAID-масиви Linux із кешем наскрізного запису, досягнувши субмілісекундної затримки при 100% збереженості даних.
     Аналіз архітектури Discord показує, що кожен її рівень спроєктований із фокусом на максимальну швидкість та оптимізацію ресурсів у реальному часі. Завдяки усуненню вузьких місць на стику програмного та апаратного забезпечення, розробникам вдалося створити гнучку інфраструктуру, яка працює без затримок навіть на мільйонних серверах.
     
     3.6 Реалізація шаблона патерна
	Для демонстрації архітектурних принципів автономності та асинхронної обробки подій реального часу нижче наведено програмну реалізацію двох критичних компонентів системи Discord на мові Python: децентралізованого генератора ідентифікаторів та фонового обробника завдань. Приклад програмного коду наведено у додатку В.
     Децентралізація генерації об'єктів (Рядки 5–36): Клас DiscordSnowflakeGenerator дозволяє серверам шлюзу (Gateway) миттєво створювати унікальні 64-бітні ID на основі часу (зміщеного на епоху компанії від 2015 року) за допомогою побітових зсувів. Це прибирає потребу у централізованій базі даних для отримання порядкових номерів і забезпечує автоматичне хронологічне сортування «з коробки».
     Асинхронний Non-blocking I/O (Рядки 45–60, 68–76): Метод on_message_create демонструє максимальну швидкість реакції шлюзу. Замість очікування виконання важких операцій індексації в пошук та розсилки сповіщень (що заблокувало бы потік майже на секунду), завдання миттєво скидаються в асинхронну чергу task_queue. Самостійний фоновий процес background_worker розгрібає їх у тлі, зберігаючи стабільно низьку затримку шлюзу для нових подій.

      23                 while timestamp <= self.last_timestamp:
      24                     timestamp = self._get_current_ms()
      25         else:
      26             self.sequence = 0
      27 
      28         self.last_timestamp = timestamp
      29 
      30         # Порозрядне зміщення (Bit Shifting) для формування фінального 64-бітного ID
      31         return (
      32             ((timestamp - self.discord_epoch) << 22) |
      33             (self.datacenter_id << 17) |
      34             (self.worker_id << 12) |
      35             self.sequence
      36         )

     В.2.1 Запит 1: Децентралізована генерація Snowflake ID
     Вхідний запит: Напиши на Python автономний клас DiscordSnowflakeGenerator. Мені потрібно генерувати унікальні 64-бітні сортовані ID на основі поточної мітки часу в мілісекундах зі зміщенням під епоху Discord (1 січня 2015 року). Використовуй побітові зсуви для пакування мітки часу, datacenter_id, worker_id та інкременту послідовності.
     Відповідь:
      1  Для реалізації алгоритму типу Twitter/Discord Snowflake нам потрібно запакувати кілька компонентів у одне 64-бітне число за допомогою побітових операцій зсуву (<<) та побітового АБО (|).
      2  Ось готовий клас на Python:
      3  
      4  class DiscordSnowflakeGenerator:
      5      def __init__(self, worker_id: int, datacenter_id: int):
      6          self.discord_epoch = 1420070400000  # Епоха Discord (1 січня 2015 р.)
      7          self.worker_id = worker_id
      8          self.datacenter_id = datacenter_id
      9          self.sequence = 0
      10         self.last_timestamp = -1
      11 
      12     def generate_id(self) -> int:
      13         timestamp = int(time.time() * 1000)
      14         
      15         if timestamp == self.last_timestamp:
      16             self.sequence = (self.sequence + 1) & 4095
      17         else:
      18             self.sequence = 0
      19             
      20         self.last_timestamp = timestamp
      21         
      22         # Порозрядне зміщення (Bit Shifting) для формування фінального 64-бітного ID
      23         return (
      24             ((timestamp - self.discord_epoch) << 22) |
      25             (self.datacenter_id << 17) |
      26             (self.worker_id << 12) |
      27             self.sequence
      28         )
      29 
      30 Як це працює архітектурно:
      31 
      32 * Мітка часу (Біти 22-63): Зсув на 22 біти вліво виділяє старшу частину числа під мілісекунди. Це гарантує хронологічне сортування.
      33 * Datacenter & Worker ID (Біти 12-21): Ідентифікують конкретний сервер-шлюз у хмарі, що виключає колізії між різними машинами.
      34 * Послідовність (Біти 0-11): Інкремент для колізій в межах однієї й тієї ж мілісекунди (маска & 4095 дозволяє згенерувати до 4096 унікальних ID за 1 мс).
     Внесок автора:
     Здійснено аналіз згенерованого коду на відповідність вимогам розподіленої генерації ключів та перевірено правильність розрахунку часової епохи.
     
     В.2.2 Запит 2: Асинхронний воркер та неблокуюча черга шлюзу
     Вхідний запит: Напиши клас DiscordGatewayProcessor на Python за допомогою бібліотеки asyncio. Реалізуй метод on_message_create, який миттєво повертає відповідь, але скидає важкі завдання в асинхронну чергу asyncio.Queue. Також створи нескінченний фоновий процес background_worker, який розгрібає ці таски в тлі без блокування шлюзу.
     Відповідь:
      1  Для реалізації неблокуючої обробки подій у реальному часі (Low Latency Gateway) найкраще використати шаблон «Воркер-Черга» через асинхронність asyncio. Метод-тригер буде лише реєструвати подію, а важкий I/O виконуватиметься у фоні.
      2  Реалізація архітектурного вузла шлюзу:
      3  
      4  class DiscordGatewayProcessor:
      5      def __init__(self, worker_id: int, datacenter_id: int):
      6          self.task_queue = asyncio.Queue()  # Асинхронна черга задач
      7  
      8      async def background_worker(self):
      9          """Нескінченний фоновий процес (Worker) для обслуговування черги."""
      10         while True:
      11             task = await self.task_queue.get()
      12             task_type = task.get("type")
      13             data = task.get("data")
      14             
      15             if task_type == "INDEX_SEARCH":

      19                 
      20             self.task_queue.task_done()
      21 
      22     async def on_message_create(self, guild_id: int, content: str):
      23         """Миттєвий тригер шлюзу на нову подію."""
      24         message_id = self.id_generator.generate_id()
      25         
      26         # Неблокуюче скидання інфраструктурних задач в асинхронну чергу
      27         await self.task_queue.put({"type": "INDEX_SEARCH", "data": {"id": message_id}})
      28         await self.task_queue.put({"type": "PUSH_NOTIFY", "data": {"guild_id": guild_id}})

      31
